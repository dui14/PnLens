## 1. Overview & Security Principles

Integrating exchange APIs into analytics platforms requires strict security isolation. The primary goal is to fetch asset balances, open orders, historical trade fills, and position risks without exposing user accounts to unauthorized trading, borrowing, or withdrawal capabilities.

### Read-Only Scope Definition
A **Read-Only API Key** is restricted exclusively to query operations. It permits applications to read account state while enforcing hard blocks on execution endpoints:

* **Permitted Scope**: `Enable Reading` (retrieving account balances, trade history, open orders, and position risk).
* **Prohibited Scope**: Spot & Margin Trading, Futures Trading, Asset Withdrawals, Internal Transfers, Margin Borrowing/Repaying, and Option Trading.

> **Critical Security Warning for Users**: Read-Only API keys do not allow funds to be moved or traded, but they expose full financial history, total net worth, asset holdings, active positions, and trading patterns. Applications must treat Read-Only credentials as sensitive data: encrypt keys at rest, enforce server IP restrictions, and audit database access.

## 2. Authentication Architecture: HMAC-SHA256 vs. Ed25519

Binance supports two cryptographic authentication mechanisms for signed REST API endpoints: **HMAC-SHA256** (symmetric) and **Ed25519** (asymmetric).

### Architectural Comparison

| Feature | HMAC-SHA256 (Symmetric) | Ed25519 (Asymmetric) |
| :--- | :--- | :--- |
| **Key Pair Generation** | Generated by Binance (API Key & Secret Key). | Generated by Application Backend (Public & Private Key Pair). |
| **Secret Storage** | Secret Key is shown once on Binance; user must copy and submit it to your backend. | Private Key **never** leaves server infrastructure. Only Public Key is uploaded to Binance. |
| **User Experience** | User handles raw secret keys, increasing risk of exposure or phishing. | User only pastes the Public Key into Binance; zero secret handling required. |
| **Security Posture** | High risk if Secret Key is intercepted in transit or exposed in client UI. | Superior security: Private key remains isolated in server Vault / KMS / HSM. |

### Recommended Workflow for Multi-User Applications (Ed25519)
For community platforms and SaaS products, **Ed25519 asymmetric signing** is strongly recommended:

1. **Backend Key Pair Generation**: Server programmatically generates a unique Ed25519 key pair per user.
2. **Public Key Registration**: Server provides the Ed25519 Public Key (PEM format) to the user. The user pastes this public key into Binance's API Management UI to generate an API Key.
3. **API Key Submission**: User submits only their Binance API Key back to your platform.
4. **Private Key Isolation**: Server encrypts the Ed25519 Private Key at rest (e.g., via AWS KMS or HashiCorp Vault), separate from standard application databases. The private key is never logged and never sent to client devices.

### Request Headers & Signing Parameters
All authenticated REST requests require specific HTTP headers and signing parameters:

* **HTTP Header**: `X-MBX-APIKEY: <api_key>`
* **Mandatory Parameters**:
  * `timestamp`: Unix timestamp in milliseconds (e.g., `1729241635546`).
  * `signature`: Cryptographic signature generated over the query string and request body.
  * `recvWindow` *(Optional)*: Time window in milliseconds during which request remains valid (default: `5000` ms, max: `60000` ms).

## 3. API Key Permission Verification

Applications must query Binance's API key permission status immediately upon receiving an API Key, rejecting any key that has write, trade, or withdrawal permissions enabled.

### Verification Endpoint
* **HTTP Method**: `GET`
* **Path**: `/sapi/v1/account/apiRestrictions`
* **Security Type**: `USER_DATA` (SIGNED)
* **Base URL**: `https://api.binance.com`

### Permission Enforcement Rules

| Field Name in Response | Expected Value | Application Enforcement Action |
| :--- | :--- | :--- |
| `enableReading` | `true` | **Pass**: Reading permission is active. |
| `enableSpotAndMarginTrading` | `false` | **Reject Key**: Spot trading MUST be disabled. |
| `enableWithdrawals` | `false` | **Reject Key**: Withdrawal MUST be disabled. |
| `enableInternalTransfer` | `false` | **Reject Key**: Internal transfer MUST be disabled. |
| `permitsUniversalTransfer` | `false` | **Reject Key**: Universal transfer MUST be disabled. |
| `enableFutures` | `false` *(or `true` if reading Futures)* | Reject key if futures execution privileges are enabled when trade execution is not intended. |
| `ipRestrict` | `true` *(Recommended)* | Warn user if IP whitelist restriction is absent. |

## 4. Core Read-Only REST API Endpoints Reference

All endpoints listed below strictly match official Binance REST API specifications.

### Base URLs
* **Spot REST API Base URL**: `https://api.binance.com` *(Alternatives: `https://api1.binance.com`, `https://api-gcp.binance.com`)*
* **USDⓈ-M Futures REST API Base URL**: `https://fapi.binance.com`
* **COIN-M Futures REST API Base URL**: `https://dapi.binance.com`

---

### 4.1 Spot Trading & Account Endpoints

#### 1. Account Information & Balances
* **HTTP Method**: `GET`
* **Endpoint**: `/api/v3/account`
* **Security Type**: `USER_DATA` (SIGNED)
* **Request Weight**: 20
* **Parameters**: `timestamp` (Required), `recvWindow` (Optional)
* **Description**: Returns account status, asset balances (free and locked), and permissions.

#### 2. Account Trade List (Fills)
* **HTTP Method**: `GET`
* **Endpoint**: `/api/v3/myTrades`
* **Security Type**: `USER_DATA` (SIGNED)
* **Request Weight**: 20
* **Parameters**:
  * `symbol` (String, Required): Trading pair (e.g., `BTCUSDT`).
  * `orderId` (Long, Optional): Filter trades from order ID.
  * `startTime` (Long, Optional): Start time in ms.
  * `endTime` (Long, Optional): End time in ms.
  * `fromId` (Long, Optional): Trade ID to fetch from.
  * `limit` (Int, Optional): Default 500; max 1000.
* **Description**: Returns executed trade history for a specified symbol, including trade price, executed quantity, commission fee (`commission`), and fee asset (`commissionAsset`).

#### 3. All Orders (Order History)
* **HTTP Method**: `GET`
* **Endpoint**: `/api/v3/allOrders`
* **Security Type**: `USER_DATA` (SIGNED)
* **Request Weight**: 20
* **Parameters**: `symbol` (Required), `orderId` (Optional), `startTime` (Optional), `endTime` (Optional), `limit` (Optional, max 1000).
* **Description**: Retrieves all orders (completed, canceled, or expired) for a symbol.

#### 4. Current Open Orders
* **HTTP Method**: `GET`
* **Endpoint**: `/api/v3/openOrders`
* **Security Type**: `USER_DATA` (SIGNED)
* **Request Weight**: 6 for a single symbol; 80 when `symbol` is omitted.
* **Parameters**: `symbol` (Optional).
* **Description**: Returns currently active open orders.

---

### 4.2 Futures Trading (USDⓈ-M & COIN-M) Endpoints

#### 1. Futures Account Information
* **HTTP Method**: `GET`
* **Endpoint**: `/fapi/v2/account` *(USDⓈ-M)* | `/dapi/v1/account` *(COIN-M)*
* **Security Type**: `USER_DATA` (SIGNED)
* **Request Weight**: 5
* **Description**: Fetches total futures wallet balance, margin balance, and account position overview.

#### 2. Position Information (Position Risk)
* **HTTP Method**: `GET`
* **Endpoint**: `/fapi/v2/positionRisk` *(USDⓈ-M)* | `/dapi/v1/positionRisk` *(COIN-M)*
* **Security Type**: `USER_DATA` (SIGNED)
* **Request Weight**: 5
* **Parameters**: `symbol` (Optional).
* **Description**: Fetches current open position quantities, entry prices, mark prices, unrealized profit/loss (`unrealizedProfit`), leverage, and liquidation prices.

#### 3. Futures User Trades (Fills)
* **HTTP Method**: `GET`
* **Endpoint**: `/fapi/v1/userTrades` *(USDⓈ-M)* | `/dapi/v1/userTrades` *(COIN-M)*
* **Security Type**: `USER_DATA` (SIGNED)
* **Request Weight**: 5
* **Parameters**: `symbol` (Optional for USDⓈ-M, Required for COIN-M), `startTime` (Optional), `endTime` (Optional), `fromId` (Optional), `limit` (Optional, max 1000).
* **Description**: Returns executed trades for futures contracts.

#### 4. Get Income History (PnL, Funding Fees & Commissions)
* **HTTP Method**: `GET`
* **Endpoint**: `/fapi/v1/income` *(USDⓈ-M)* | `/dapi/v1/income` *(COIN-M)*
* **Security Type**: `USER_DATA` (SIGNED)
* **Request Weight**: 30
* **Parameters**:
  * `symbol` (String, Optional)
  * `incomeType` (String, Optional): `REALIZED_PNL`, `FUNDING_FEE`, `COMMISSION`, `INSURANCE_CLEAR` (Liquidation penalty), `REFERRAL_KICKBACK`.
  * `startTime` (Long, Optional)
  * `endTime` (Long, Optional)
  * `limit` (Int, Optional): Default 100; max 1000.
* **Description**: Primary endpoint for querying realized PnL, funding fee payments/rebates, trading fees, and liquidation penalties.

#### 1. Margin Account Details
* **HTTP Method**: `GET`
* **Endpoint**: `/sapi/v1/margin/account`
* **Security Type**: `USER_DATA` (SIGNED)

#### 2. Margin Trade List

#### 3. Margin Interest History
* **HTTP Method**: `GET`
* **Endpoint**: `/sapi/v1/margin/interestHistory`
* **Security Type**: `USER_DATA` (SIGNED)
* **Request Weight**: 1
* **Parameters**: `asset` (Optional), `startTime` (Optional), `endTime` (Optional), `limit` (Optional).
* **Description**: Retrieves interest accrued on borrowed assets.

## 5. Data Processing & PnL Calculation Methodology

### 5.1 Realized PnL vs. Unrealized PnL

Accurate performance measurement requires separating closed transaction gains/losses (Realized PnL) from active position open gains/losses (Unrealized PnL).

#### Spot Realized PnL Calculation
Spot markets require tracking asset inventory cost basis using **FIFO (First-In, First-Out)** or **Weighted Average Cost**:

$$\text{Realized PnL} = (\text{Sell Price} - \text{Cost Basis}) \times \text{Quantity} - \text{Trading Fees}$$

#### Futures Realized PnL
For Futures contracts, Realized PnL is tracked directly via `GET /fapi/v1/income` where `incomeType = "REALIZED_PNL"`.

#### Unrealized PnL Calculation
* **Spot Holdings**:
  $$\text{Unrealized PnL} = (\text{Current Market Price} - \text{Average Buy Price}) \times \text{Holding Quantity}$$

* **Futures Linear Contracts (USDⓈ-M)**:
  $$\text{Unrealized PnL} = (\text{Mark Price} - \text{Entry Price}) \times \text{Position Size} \times \text{Direction}$$
  *(where Direction is $+1$ for Long positions and $-1$ for Short positions)*.

* **Futures Inverse Contracts (COIN-M)**:
  $$\text{Unrealized PnL} = \left(\frac{1}{\text{Entry Price}} - \frac{1}{\text{Mark Price}}\right) \times \text{Contract Size} \times \text{Quantity}$$

---

### 5.2 Trade History as Ground Truth

Account balance changes ($\Delta \text{Balance} = \text{Balance}_{t_2} - \text{Balance}_{t_1}$) MUST NOT be used for PnL calculation. Capital movements—such as crypto deposits, fiat withdrawals, internal wallet transfers (e.g. Spot to Futures), and Earn subscriptions—alter balance totals without representing trading gains or losses. Trade fill logs (`myTrades`, `userTrades`, `income`) constitute the sole ground truth.

---

### 5.3 Comprehensive Fee & Expense Deductions

To calculate net performance, all transaction expenses must be netted against gross trading returns:

1. **Spot Trading Fees**: Deduct `commission` from `GET /api/v3/myTrades`. Account for fees paid in BNB, base asset, or quote asset.
2. **Futures Funding Fees**: Net funding payments from `GET /fapi/v1/income` (`incomeType = "FUNDING_FEE"`). Funding rates can be positive (rebate) or negative (expense).
3. **Liquidation Penalty Fees**: Include forced liquidation clearance fees from `GET /fapi/v1/income` (`incomeType = "INSURANCE_CLEAR"`).
4. **Margin Borrowing Interest**: Deduct cumulative interest paid from `GET /sapi/v1/margin/interestHistory`.

---

### 5.4 Timestamps, day boundary, and CSV import

* **Timestamps**: Binance API timestamps are Unix epoch milliseconds. Signing and request windows stay on that clock.
* **PnLens day boundary**: daily, weekly, monthly, and yearly aggregates use Vietnam time, fixed UTC+7, from `APP_UTC_OFFSET_MINUTES = 420` in one module (`spec/features/pnl-day-boundary.md`). They do not use UTC midnight and they do not use the server's local zone.
* **Binance Download Center CSV Fallback**: REST API endpoints enforce time window lookback limits (e.g., historical trades beyond 3 to 6 months require pagination or time chunking). For historical records preceding API limits or specialized product lines, provide an interface allowing users to import official CSV exports from Binance Download Center.

## 6. User Safety & Configuration Best Practices

Provide clear user guidance for API Key generation:

1. Log in to **Binance API Management**.
2. Select **Create API Key** (Choose **Self-generated API Key** for Ed25519 asymmetric setup).
3. Under API Restrictions, check **Enable Reading** only.
4. **Uncheck** all trading, withdrawal, and transfer permissions.
5. Enable **Restrict access to trusted IPs only** and enter your server static IP address(es).
6. Complete 2FA verification.

```
[System Security Checklist]
✔ Read Permission Only Enabled
❌ Spot & Margin Trading Disabled
❌ Futures Trading Disabled
❌ Withdrawals Disabled
❌ Universal Transfers Disabled
✔ Server IP Whitelist Enforced
✔ Private Keys Encrypted at Rest (AES-256-GCM / KMS)
```

## 7. API Rate Limiting & Error Handling

### Rate Limits & Weight System
Binance API limits are calculated based on request weights per minute:

* **IP Rate Limit**: 6,000 weight per minute per IP address.
* **HTTP 429 (Too Many Requests)**: Returned when request weight is exceeded. The application must pause request execution immediately.
* **HTTP 418 (IP Auto-Banned)**: Returned if requests continue after a 429 status code. Ban duration lasts between 2 minutes and 3 days.
* **Retry-After Header**: Always inspect the `Retry-After` HTTP header in 429/418 responses to specify back-off delay.

### Time Synchronization & `recvWindow`
Requests with a timestamp discrepancy exceeding server limits are rejected with error `-1021 INVALID_TIMESTAMP`.

* **Timestamp Condition**:
  $$\text{server\_time} - \text{recvWindow} \le \text{timestamp} < \text{server\_time} + 1000$$
* **Best Practice**: Keep server clocks NTP-synchronized and pass a `recvWindow` of `5000` ms to `10000` ms to accommodate network latency.
